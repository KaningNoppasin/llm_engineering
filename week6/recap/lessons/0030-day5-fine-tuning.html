Fine-tuning — and when it fails

The counterintuitive lesson: fine-tuning a frontier model made it worse.

Why this matters for the switch: everyone wants to say "we fine-tuned a model." The senior insight is knowing when not to. Today's result — fine-tuning a capable model on this task hurt it — is the kind of judgment that separates real engineers from résumé-driven ones.

Today's win

You can run a supervised fine-tuning job via the OpenAI API, and explain when fine-tuning helps versus when prompting/RAG (or a from-scratch model) is the better tool.

What fine-tuning is for

Supervised fine-tuning (SFT) trains a model on input→output examples to change its behavior — tone, format, fixing specific failures — not to pour new knowledge into an already-capable model. When you fine-tune via the OpenAI API, it trains small LoRA adapters behind the scenes, not the whole model.

Key concepts

  • The data is JSONL chat format. Each line is a {"messages": [user, assistant]} example — the assistant message is the target answer.
  • Three stages. Upload the training file → create & monitor the fine-tuning job (watch the loss) → test the resulting custom model variant.
  • Start small. OpenAI suggests 50–100 examples, one epoch — only scale up if few-shot prompting genuinely fails.
  • The result: it got worse. Fine-tuning gpt-4o-mini on 20k price examples gave $75.91 MAE — worse than the untuned model (~$67). The model already knew prices; the examples added noise.
  • Use SFT for style, not knowledge. Tone/voice, strict output format, fixing a recurring mistake — yes. Teaching domain facts to a strong model — usually no.
  • For knowledge, reach for RAG/prompting (Week 5) — or, if you own the problem, train your own model from scratch.
  • The redemption. A specialized 289M-parameter deep net trained from scratch on all 800k items hit $46.49 MAE — beating Claude Opus and nearly matching GPT-5.1. Specialization beats scale when the domain is narrow.

The code shape to memorize

# 1. each training example is a chat-format pair
def messages_for(item):
    return [{"role": "user",      "content": f"Estimate the price:\n{item.summary}"},
            {"role": "assistant", "content": f"${item.price:.2f}"}]

# 2. upload the JSONL file, then start the job
f = openai.files.create(file=open("train.jsonl", "rb"), purpose="fine-tune")
job = openai.fine_tuning.jobs.create(
    training_file=f.id, model="gpt-4.1-nano-2025-04-14",
    hyperparameters={"n_epochs": 1}, suffix="pricer")

# 3. monitor the run
openai.fine_tuning.jobs.list_events(fine_tuning_job_id=job.id, limit=10)
Interview-ready framing: "Fine-tune, RAG, or prompt?" — Prompt/few-shot first (cheapest). RAG when you need private/fresh knowledge. Fine-tune to lock in behavior (style/format) or when prompting plateaus. Fine-tuning a strong model to add facts often backfires — exactly what happened today.
