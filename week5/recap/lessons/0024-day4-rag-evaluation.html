Evaluating RAG

Turn the "vector-similarity hack" into a measured, iterable system.

Why this matters for the switch: anyone can wire up a RAG demo; the engineer who gets hired can measure it and improve it on purpose. Evaluation is what separates a science project from a production system — and it builds on Week 4's metrics discipline.

Today's win

You can measure retrieval with MRR, judge answer quality with an LLM-as-judge returning structured output, and iterate chunking/embeddings to move the score.

Two halves of evaluation

RAG can fail at retrieval (wrong chunks) or at answering (good chunks, bad answer). So you measure both: retrieval metrics on the chunks, and answer-quality metrics on the final text — the latter via an LLM-as-a-judge.

Key concepts

  • MRR (Mean Reciprocal Rank). 1 ÷ the position of the first relevant chunk, averaged over tests. MRR = 1.0 means the right chunk was always first; 0.5 means second on average.
  • nDCG rewards ranking all relevant chunks high, not just the first; keyword coverage / recall checks the needed facts appear in the top-k.
  • Favor recall over precision. Missing context is fatal (the LLM can't invent it); extra noise the LLM can usually ignore.
  • LLM-as-a-judge. Have a model score the generated answer vs a reference on accuracy / completeness / relevance (1–5) — using structured outputs (a Pydantic schema) so you get typed JSON, not prose to parse.
  • Golden test data. Curate ~150 questions with expected keywords and reference answers (loaded as Pydantic models). Categories: direct-fact, temporal, and the hard ones — spanning (multi-chunk) and holistic.
  • Iterate the levers. Chunk size and embedding model move the score: in the lesson, 500-char chunks + OpenAI text-embedding-3-large beat 1000-char + MiniLM (MRR 0.73 → 0.79, coverage 81% → 92%).
  • Control your variables. When comparing chunk sizes, hold total context constant so you're measuring granularity, not context length.

The code shape to memorize

from pydantic import BaseModel

# golden test case + judge schema as Pydantic models
class TestQuestion(BaseModel):
    question: str; keywords: list[str]; reference_answer: str

class AnswerEval(BaseModel):
    feedback: str; accuracy: float; completeness: float; relevance: float

# MRR: reciprocal of the first relevant chunk's position
def reciprocal_rank(chunks, keyword):
    for i, c in enumerate(chunks, start=1):
        if keyword in c.page_content.lower(): return 1 / i
    return 0

# LLM-as-judge with structured output (typed result, no parsing)
verdict = client.beta.chat.completions.parse(model=JUDGE, messages=[...],
                                              response_format=AnswerEval)
Interview-ready framing: "How do you know your RAG got better?" — A frozen golden set + MRR/nDCG for retrieval + an LLM judge for answers. Change one lever (chunk size, embedding model), re-run, compare. Without a baseline, "it feels better" is not evidence.
