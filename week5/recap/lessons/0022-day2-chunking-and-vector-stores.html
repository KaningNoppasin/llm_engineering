Chunking & vector stores

Turning documents into searchable vectors — the ingest half of RAG.

Why this matters for the switch: retrieval quality is decided here, at ingest. How you chunk and which embedding model you pick make or break a RAG system — and these are the knobs you'll be expected to tune on the job.

Today's win

You can split documents into overlapping chunks, embed them, and store them in a Chroma vector database ready for semantic search.

The ingest pipeline

Load → chunk → embed → store. Documents are split into chunks, each chunk is turned into a vector by an embedding model, and the (text, vector) pairs go into a vector database for fast similarity search.

Key concepts

  • Chunk, don't embed whole docs. A question usually concerns one passage, not the whole file. Many small vectors per document match far better than one big one.
  • RecursiveCharacterTextSplitter splits on natural boundaries (paragraphs → lines → spaces), controlled by chunk_size and chunk_overlap.
  • Overlap prevents cut answers. chunk_overlap=200 repeats a little text across neighbours so a fact split across a boundary still lands whole in some chunk.
  • The encoder makes the vector; the DB stores it. Two separate components: an embedding model (OpenAIEmbeddings, or open all-MiniLM-L6-v2) and a vector store.
  • Dimensions vary by model. all-MiniLM-L6-v2 = 384, text-embedding-3-small = 1536, -large = 3072. Bigger generally separates meaning better — but costs more.
  • Vector DBs: Chroma (lightweight, local, SQLite-backed — used here), FAISS (in-memory), Pinecone/Weaviate (managed, paid). They do similarity search, not SQL.
  • t-SNE projects high-dim vectors to 2D/3D so you can see whether related chunks cluster — a quick visual check of embedding quality.

The code shape to memorize

from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings

# 1. chunk
splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = splitter.split_documents(documents)

# 2. embed + 3. store (one call builds the vector DB)
embeddings = OpenAIEmbeddings()                  # or HuggingFaceEmbeddings(...)
vectorstore = Chroma.from_documents(documents=chunks, embedding=embeddings,
                                     persist_directory="vector_db")
Interview-ready framing: "How do you pick chunk size?" — There's no universal answer; it's empirical. Smaller chunks (e.g. 500) often retrieve more precisely but risk losing context; you measure it (Day 4). And the embedding model at ingest must match the one at query — different dimensions = error.
