RAG & vector embeddings

Grounding the model in your own knowledge — from keyword lookup to meaning.

Why this matters for the switch: RAG is the most-deployed LLM pattern in industry — every "chat with your docs" product is RAG. It's also the cure for hallucination on private/fresh data. If you can build and explain RAG, you can build what most companies actually want.

Today's win

You can explain why semantic vector search beats keyword lookup, and build a naive RAG that injects retrieved context into the prompt.

The big idea

An LLM only knows its training data. RAG (Retrieval-Augmented Generation) fixes that: retrieve the documents relevant to a question, stuff them into the prompt, then generate the answer grounded in that context. Week 2's "primitive RAG" (an if "belt" in message) was the toy version — this week makes it real.

Key concepts

  • Naive RAG = keyword lookup. Match words in the question to documents, inject their text. Brittle: "Heathrow flights" won't match "London airport prices" — different words, same meaning.
  • The fix is semantic search. Turn text into vector embeddings (lists of numbers capturing meaning) and retrieve by closeness in vector space, not string overlap.
  • Two kinds of model. Generative/autoregressive models (GPT, Claude) produce text; encoder/embedding models (BERT, OpenAI text-embedding-3) map text → one vector. RAG uses an encoder to retrieve, a generator to answer.
  • A vector is a point in meaning-space. Typically 300–3072 dimensions; similar meanings land near each other, so "flights to London" ≈ "Heathrow ticket prices".
  • word2vec showed meaning is arithmetic. The classic king − man + woman ≈ queen — vectors encode relationships you can add and subtract.
  • Cosine similarity ranks how close two vectors are; retrieval grabs the top-k nearest documents to the query vector.
  • RAG ≠ fine-tuning. You add knowledge at inference time via the prompt — no retraining, and you can update the knowledge base instantly.

The code shape to memorize (naive RAG)

# 1. load a knowledge base keyed by name
knowledge = {Path(f).stem.split()[-1].lower(): open(f).read()
             for f in glob.glob("knowledge-base/employees/*")}

# 2. keyword lookup -> relevant context (the BRITTLE part)
def get_context(message):
    words = message.lower().split()
    return [knowledge[w] for w in words if w in knowledge]

# 3. inject context into the prompt, then generate
system = SYSTEM_PREFIX + "\n\nContext:\n" + "\n\n".join(get_context(q))
openai.chat.completions.create(model="gpt-4.1-nano", messages=[...])
Interview-ready framing: "RAG vs fine-tuning?" — RAG injects knowledge at query time (fast to update, cites sources, no training); fine-tuning bakes behavior into weights (Week 6–7). Most "chat with your data" needs are RAG, not fine-tuning.
